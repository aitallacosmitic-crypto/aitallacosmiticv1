# Security and operating model

The SPA has no privileged backend key. Requests use Supabase bearer tokens, not ambient session cookies. All authorization is in Postgres/Storage. The client reads its own roles for navigation only. Never store a role in editable Auth user metadata. Verify the Supabase project's exposed schemas: `public` and `graphql_public`, never `private`.

| Principal        | Access                                                                                                                                                                                                                                |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Anonymous        | Published active products and corresponding image metadata, categories, public settings, approved reviews. No order creation or stock writes. Public Storage objects are intentionally public by URL; never upload private documents. |
| Customer         | Own profile, address book, wishlist, order snapshots and status history. May review a delivered purchase once, pending moderation. Only signed-in, active customers can submit COD orders. WhatsApp enquiries need no account.        |
| Product manager  | Catalog, public imagery, categories, promotions, moderation and reasoned inventory adjustments. No customer directory/order access beyond personal customer rights.                                                                   |
| Order manager    | Customers, orders, status/tracking updates, private notes and invoices. Cannot set prices, adjust inventory manually or assign roles.                                                                                                 |
| Customer support | Customer/order lookup and internal notes. Cannot change status, stock, totals or roles.                                                                                                                                               |
| Super admin      | Staff operations, settings, purchase suspension, audit inspection. Staff provisioning remains an operator operation, not public registration.                                                                                         |

`place_order` uses a fixed search path and explicit auth checks. It serializes requests for the same buyer, locks product rows in stable UUID order, checks quantities and stock, locks coupon capacity, calculates trusted prices and verifies the reviewed total. Order header, snapshots, deductions, usage and history commit or roll back together. The client retains a retry key until receipt; unique `(user_id,idempotency_key)` prevents double deduction. Five successful orders per buyer per hour are permitted. Failed attempts do not consume inventory. Coupons stack **after** the best applicable per-product quantity tier on the sale or base price. Shipping thresholds apply to discounted merchandise. Cancellation/return restores stock once; used coupons remain consumed. Returned goods must be quarantined with a reasoned stock adjustment if not resalable.

Staff changes are audited without copying customer addresses, delivery instructions or credentials into logs. Private notes live in their own RLS table. A suspended customer cannot place new orders, but can still access order history. Adjusting identity/login access is an Auth operator action. A product that has ledger movements or order references cannot be hard-deleted; retire it instead. MFA for staff, verification email, short session policies and abuse protection must be configured with the Auth provider before launch.

## Operational controls before launch

- Verify backup restoration, not just backup creation. Inspect schema and storage bucket names before applying migrations. DDL conflicts intentionally abort. Do not `db reset` against any existing project. Rehearse restore, migration, rollback and order reconciliation on staging.
- Enable email verification, production SMTP, allowed callback URLs, appropriate Auth rate limits and CAPTCHA as warranted. Set upstream rate/traffic limits, PostgreSQL statement timeouts, monitoring and alerts. An order quota alone does not protect every API from abuse.
- Enforce HTTPS; deploy with the included CSP and security headers. For a custom Supabase domain, explicitly change `connect-src` to its HTTPS/WSS origin. Do not allow arbitrary script origins. If a payment provider is added, implement idempotent verified webhooks on a trusted server; never collect card details in this SPA.
- Use distinct preview and production projects. A staging Vercel/Netlify preview must not receive production customer data. Operators should test each role, email delivery/recovery, uploads, inventory and dispatch before promotion. Revoke staff roles in the database when access changes.
- Storage buckets accept JPEG/PNG/WebP, maximum 5 MiB. Uploaders must be authorized staff; do not accept public uploads. Removing image metadata does not delete a file customers might still reference. Periodically reconcile unused objects in Storage, with backup and owner approval.
- Source photos remain hosted externally; verify availability and rights. Transfer approved originals into product-images before decommissioning that host. Check the original product/medical wording and local privacy, return and consumer-law obligations with the merchant before opening sales.
